## 1. 目的

本文档定义 Task Manager 项目的**开发流程规范**，使每一次代码产出都可追溯、可验证、可回滚。核心目标有三条：

1. **过程可复现**：任何一轮开发都有明确的入口条件、出口条件与验证证据。
2. **需求可追溯**：每条代码变更都能回指到具体需求编号（FR / EX / NFR / DC / UI）。
3. **质量可度量**：以单元测试覆盖率、Lint 告警数、手工验收通过率作为客观质量指标。

本项目采用 **Agentic 开发模式**（人给目标与验收口径，Agent 执行，人在浏览器与测试中确认），因此流程规范的重点是"每轮循环的约束"与"出口门禁"，而非人员分工。

---

## 2. 角色与职责

| 角色 | 承担者 | 职责 |
| --- | --- | --- |
| 需求负责人（PO） | 用户 | 确认需求范围与优先级、裁决口径冲突、验收每轮产出 |
| 开发执行者（Agent） | AiWork | 按本轮计划实现代码与测试、自检、提交 |
| 验证人 | 用户 + Agent | 执行手工验收清单与自动化测试，记录证据 |
| 变更管理员 | 用户 | 批准需求变更，触发第 9 章变更控制流程 |

单人项目下角色可重叠，但**"提出需求"与"验收需求"不得由同一轮的执行者自行判定通过**：Agent 不得以"代码已写完"替代验收证据。

---

## 3. 迭代流程：计划 – 执行 – 确认

每一轮迭代严格遵循三阶段，未通过确认阶段不得进入下一轮。

### 3.1 计划阶段（Plan）

本轮开始前，必须书面给出以下 5 项（可写在提交信息、对话或 `docs/迭代记录.md` 中）：

1. **本轮目标**：一句话说明要达成的可观察结果。
2. **涉及需求编号**：本轮覆盖的 FR / EX / NFR / DC / UI 清单。
3. **变更文件清单**：预计新增或修改的文件路径。
4. **本轮 DoD**：见第 8 章，逐条可勾选。
5. **风险与依赖**：是否依赖前一轮未完成项、是否引入新依赖。

### 3.2 执行阶段（Do）

- 只实现本轮计划内的需求，**禁止顺手改动计划外的既有行为**（发现必要改动时登记为遗留问题，另开一轮）。
- 新增功能必须同时新增或更新对应的 Vitest 单元测试（见第 7 章）。
- 遵守第 6 章代码规范与第 5 章目录结构约定。
- 自检：`npm run lint`、`npm run test:unit`、`npm run build` 三条命令全部通过。

### 3.3 确认阶段（Check）

按顺序执行，任一步失败即回到执行阶段修复，不得跳过：

| 步骤 | 动作 | 通过判据 |
| --- | --- | --- |
| C1 | 启动 `npm run dev`，在浏览器打开应用 | 页面正常渲染，控制台无 error 级日志 |
| C2 | 按 `04-测试计划与用例.md` 中本轮对应的手工验收项逐条操作 | 每条实际结果 = 预期结果 |
| C3 | 刷新页面（F5）验证持久化 | 本轮涉及的数据与偏好设置未丢失 |
| C4 | `npm run test:unit -- --coverage` | 全部用例通过；核心模块覆盖率达标（第 7 章） |
| C5 | `npm run lint` | 0 error，0 warning |
| C6 | `npm run build` | 构建成功，无未解析依赖告警 |
| C7 | `git commit` | 提交信息符合第 4 章规范，且包含需求编号引用 |

**证据留存**：C2 的验收结果以勾选形式记录在 `05-验收与需求追溯矩阵.md` 的验收表中（通过 / 失败 / 不适用 + 备注）。

## 4. Git 规范

### 4.1 仓库初始化

当前工作目录 `C:\Users\David\Desktop\Task_Manager` 尚未初始化仓库，**M0 里程碑的第一项任务**即为：

```bat
cd C:\Users\David\Desktop\Task_Manager
git init -b main
```

首次提交内容为 `docs/` 文档集与 `.gitignore`，提交信息：`docs: 初始化需求文档集与开发流程规范`。

### 4.2 分支策略（简化主干流）

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 唯一长期分支 | 始终保持可运行、可构建、测试全绿 |
| `feature/M<n>-<slug>` | 单轮迭代工作分支（可选） | 迭代跨多次提交时创建，完成后以 `--no-ff` 合并回 `main` 并删除 |

单轮迭代若能在一次提交内完成，**允许直接在 `main` 提交**，以避免无意义的分支开销。

### 4.3 提交信息规范（Conventional Commits）

格式：

```
<type>(<scope>): <subject>

<body：说明动机与实现要点，可省略>

<footer：Refs: FR-01, FR-13 / BREAKING CHANGE: ...>
```

**type 取值表**

| type | 含义 |
| --- | --- |
| `feat` | 新增功能需求实现（FR / EX） |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 新增或修改测试 |
| `style` | 格式调整（不影响逻辑） |
| `perf` | 性能优化（NFR-01） |
| `build` | 构建系统与依赖变更 |
| `ci` | CI 配置变更 |
| `chore` | 杂项 |

**scope 取值**：`board`、`list`、`task`、`storage`、`theme`、`filter`、`order`、`a11y`、`deps`、`docs`。

**规则**

1. `subject` 使用祈使句、首字母小写、不超过 72 字符、结尾不加句号。
2. **footer 必须引用本轮需求编号**（`Refs: FR-05`），这是需求追溯的锚点。
3. 一次提交只做一件事；跨需求的改动拆分为多次提交。
4. 破坏性契约变更（如 localStorage schema 不兼容）必须带 `BREAKING CHANGE:` 说明，并同步更新 `02-数据与存储契约.md` 的版本号。

**示例**

```
feat(order): 支持列表与看板卡片上移下移调整顺序

新增 useTaskOrder composable，实现与相邻可见任务交换 order 并持久化；
首位禁用上移、末位禁用下移，按钮带 aria-label 与 title。

Refs: FR-13, NFR-06
```

### 4.4 提交门禁

安装 `husky` + `lint-staged`，在 `pre-commit` 钩子中对暂存文件执行 ESLint 与 Prettier 校验，失败则阻止提交。**禁止使用 `--no-verify` 绕过门禁**；确需绕过时在提交 body 中说明原因并登记遗留问题。

## 5. 目录结构约定

M0 里程碑必须确立以下结构，后续迭代不得随意新增顶层目录：

```
Task_Manager/
├─ docs/                          # 文档集（本目录）
│  ├─ 00-开发流程规范.md
│  ├─ 01-需求规格说明书.md
│  ├─ 02-数据与存储契约.md
│  ├─ 03-UI与交互规格.md
│  ├─ 04-测试计划与用例.md
│  └─ 05-验收与需求追溯矩阵.md
├─ public/
├─ src/
│  ├─ assets/                     # 静态资源与全局样式入口
│  │  └─ main.css                 # Tailwind v4 @import 与 @custom-variant dark
│  ├─ components/
│  │  ├─ common/                  # AppButton、AppModal、AppSelect、EmptyState、Banner 等无业务语义组件
│  │  ├─ task/                    # TaskForm、TaskCard、TaskListItem、TaskDeleteDialog、PriorityBadge、StatusBadge
│  │  └─ board/                   # BoardView、BoardColumn、BoardColumnHeader
│  ├─ composables/                 # useTasks、useTaskOrder、useTheme、usePrefs、useStorage、useFilters
│  ├─ constants/                   # STATUS、PRIORITY、STORAGE_KEYS、SCHEMA_VERSION、DEFAULTS
│  ├─ models/                      # 纯函数领域逻辑：taskFactory、validation、orderOps、normalize、migrate
│  ├─ types/                       # JSDoc typedef（Task、Tag、Prefs、StorageEnvelope）
│  ├─ App.vue
│  └─ main.js
├─ tests/
│  └─ unit/                        # 与 src 目录结构镜像：models/、composables/、components/
├─ .gitignore
├─ .prettierrc.json
├─ eslint.config.js
├─ index.html
├─ package.json
└─ vite.config.js
```

**分层原则**

1. `models/` 为**纯函数领域层**，不依赖 Vue、不访问 DOM 与 localStorage，是单元测试的主战场（覆盖率要求最高）。
2. `composables/` 负责状态与副作用（读写 localStorage、监听 `storage` 事件），依赖 `models/`。
3. `components/` 只负责渲染与事件转发，**不直接读写 localStorage**。
4. 依赖方向单向：`components → composables → models → constants/types`，禁止反向引用。

### 5.1 语言基线

默认采用 **JavaScript（ESM）+ JSDoc 类型注释**，不引入 TypeScript 编译链，以保持"四件套"最小依赖。若评审时决定改用 TypeScript，将影响 M0 骨架、`vite.config.js`、ESLint 配置与全部代码文件后缀，须在 M0 开始前提出。

## 6. 代码规范

### 6.1 工具链

| 工具 | 用途 | 门禁级别 |
| --- | --- | --- |
| ESLint（flat config，`eslint-plugin-vue`） | 语法与 Vue 规范检查 | error 阻断提交 |
| Prettier | 统一格式 | 由 lint-staged 自动修复 |
| Vitest + @vue/test-utils + jsdom | 单元测试 | 失败阻断提交 |
| husky + lint-staged | 提交门禁 | pre-commit |

### 6.2 命名约定

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| Vue 组件文件与组件名 | PascalCase，至少两个单词 | `TaskCard.vue`、`BoardColumn.vue` |
| composable | `useXxx` camelCase | `useTasks.js`、`useTaskOrder.js` |
| 领域纯函数 | 动宾 camelCase | `createTask()`、`swapOrder()`、`normalizeTask()` |
| 常量 | UPPER_SNAKE_CASE，集中在 `constants/` | `STORAGE_KEYS.TASKS`、`SCHEMA_VERSION` |
| 枚举值 | 全小写英文，作为数据契约的稳定标识 | `todo` / `doing` / `done`；`high` / `medium` / `low` |
| CSS 类 | Tailwind 原子类优先；自定义类用 kebab-case | `.task-card--overdue` |
| 测试文件 | `<被测文件名>.spec.js`，置于 `tests/unit/` 镜像目录 | `tests/unit/models/orderOps.spec.js` |

### 6.3 编码规则

1. 组件一律使用 `<script setup>`；禁止 Options API 与 `<script>` 混写。
2. **禁止魔法字符串**：状态值、优先级值、存储 key、字段长度上限全部引用 `constants/`。
3. 禁止在组件内直接调用 `localStorage`，必须经由 `useStorage`。
4. 所有对外部输入（localStorage 读取值、表单输入）执行校验与归一化后再进入状态。
5. 副作用（写存储、监听事件）必须在 `onScopeDispose` / `onUnmounted` 中清理。
6. 不使用 `any` 式宽松 JSDoc；公共函数必须写明 `@param` / `@returns`。
7. 提交前不得残留 `console.log`（`console.warn` / `console.error` 用于异常兜底路径除外）。

## 7. 测试规范

### 7.1 分层策略

| 层级 | 对象 | 工具 | 覆盖率要求 |
| --- | --- | --- | --- |
| 领域纯函数 | `src/models/**` | Vitest（node 环境） | **语句 100%，分支 ≥95%** |
| 状态与副作用 | `src/composables/**` | Vitest + jsdom（mock localStorage） | 语句 ≥90% |
| 组件 | `src/components/**` | Vitest + @vue/test-utils | 语句 ≥80% |
| 整体 | `src/**` | Vitest coverage | **语句 ≥80%，分支 ≥75%** |

覆盖率未达阈值时 `npm run test:unit -- --coverage` 以非零码退出，阻断确认阶段 C4。

### 7.2 必测清单（不得遗漏）

1. 任务创建：合法输入、空标题、纯空格标题、超长标题、超长描述、默认值填充、id 唯一性。
2. 任务编辑：字段更新、`updatedAt` 刷新、非法输入拒绝。
3. 任务删除：确认路径、取消路径（数据不变）。
4. 状态流转：三种状态两两切换、进入 `done` 写入 `completedAt`、离开 `done` 清除 `completedAt`。
5. 顺序调整：中间项上移/下移、首位上移无效、末位下移无效、跨状态变更后的落位、持久化后重载顺序一致。
6. 持久化：首次写入、读取还原、缺失字段补齐、JSON 损坏兜底、schema 版本不匹配兜底、localStorage 抛异常（禁用/超配额）降级。
7. 主题：切换写入偏好、重载后恢复、首次访问跟随系统偏好。
8. 校验与归一化：`normalizeTask` 对各类脏数据的处理。

### 7.3 用例命名

`describe` 使用被测单元名，`it` 使用"条件 + 预期"句式：

```js
describe('swapOrder', () => {
  it('交换相邻两项的 order 值并返回新数组', () => {})
  it('对首位任务执行上移时返回原数组且不修改入参', () => {})
})
```

测试必须**互不依赖执行顺序**，每个用例自行构造数据；禁止依赖其他用例的副作用。

## 9. 变更控制流程

需求一旦进入本文档体系，任何改动都必须走变更流程，禁止直接改代码后再补文档。

### 9.1 流程

1. **提出**：说明变更内容与动机（口头/对话即可）。
2. **影响分析**：列出受影响的需求编号、文档章节、已实现代码、已有测试。
3. **裁决**：需求负责人批准 / 驳回 / 延后到后续里程碑。
4. **登记**：在第 10 章变更记录表新增一行，分配变更号 `CR-nn`。
5. **同步文档**：更新 `01`（需求条目与一览表）、`02`/`03`（契约与 UI）、`04`（测试用例）、`05`（追溯矩阵）。
6. **实施与验证**：按第 3 章走一轮完整迭代。

### 9.2 文档版本号规则

`v<主>.<次>`：主版本 = 需求范围或数据契约发生不兼容变更；次版本 = 条目细化、补充说明、优先级调整。每次变更在文档头部"变更记录"表登记。

### 9.3 变更记录

| 变更号 | 日期 | 变更内容 | 影响需求 | 裁决 | 状态 |
| --- | --- | --- | --- | --- | --- |
| CR-01 | 2026-09-22 | 将"拖拽改状态"拆分为 FR-05（状态变更能力，P0，按钮/下拉实现）与 EX-01（跨列拖拽，P1） | FR-05、EX-01 | 批准 | 已实施 |

## 11. 风险登记
